# Skill: Cloud — Render (managed full-stack + workers/cron)

Render is a PaaS for web services, background workers, cron jobs, and managed
Postgres/Redis — **not** floci-emulated. Activates at the cloud stage when the
recorded target is `render`. Philosophy: `skills/platform-engineering.md`.

## Core principle: render.yaml as declared infra, Docker parity
The service topology (web + worker + cron + datastores) is declared in
`render.yaml` (infra-as-code) and built from a Dockerfile — reproducible and
reviewable. Keep the Docker build green locally.

## Hard rules
- All services + datastores declared in `render.yaml`; no click-ops drift.
- Config via env groups; keys mirrored in `.env`; managed DB URL injected,
  never hardcoded.
- Workers and cron are first-class — long/background work goes there, not
  smuggled into web-request handlers.
- Stateless services; state in managed Postgres/Redis or a Render disk.

## Workflow
1. **Local** — `docker compose up` mirrors the `render.yaml` topology.
2. **Deploy** — blueprint (`render.yaml`) deploy to a non-prod service.
3. **Promote** — prod + custom domain + paid instance types = **§5
   escalation**.
4. **Verify** — same image/topology local → Render; parity note in `docs/qa/`.

## Known gaps / gotchas
Free-tier services spin down (cold starts); build minutes metered; region is
per-service — keep app + DB co-located.
