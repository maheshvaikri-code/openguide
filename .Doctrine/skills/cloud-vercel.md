# Skill: Cloud — Vercel (frontend & serverless deploy target)

Vercel is a PaaS deploy target for frontend (Next.js et al.) and serverless
functions — **not** floci-emulated. Activates at the cloud stage when the
recorded target is `vercel`. Governing philosophy: `skills/platform-engineering.md`
(PaaS local-first + promotion ladder).

## Core principle: portable app, thin platform coupling
The app is 12-factor; Vercel-specifics live at the edges (config, function
signatures), never smeared through business logic. It runs the same under the
framework's own dev server and `vercel dev`.

## Hard rules
- Config via **environment variables** (Vercel project env), one set of keys
  mirrored in `.env.local`; never hardcode per-environment URLs/keys.
- No secrets in the repo or in client bundles; use Vercel env (encrypted) and
  respect `NEXT_PUBLIC_` scoping (the public prefix = intentionally public).
- Serverless functions are **stateless**; state goes to an external store, not
  function memory (cold starts wipe it).
- Preview deploys are the parity check — every PR gets one; a broken preview is
  a red test.

## Workflow
1. **Local** — framework dev server or `vercel dev`; `.env.local` holds keys.
2. **Preview** — push a branch → automatic preview deploy (the parity gate).
3. **Promote** — merge → production. Prod env + custom domains = **§5
   escalation** (paid/external), human-gated.
4. **Verify** — the same build runs local → preview → prod; record a GO/NO-GO
   in `docs/qa/` on first promotion.

## Known gaps / gotchas
Function timeout + payload limits and cold starts differ from a long-running
server — don't design around persistent connections. Edge runtime lacks native
Node APIs. Build minutes and bandwidth are metered — a §5 cost item at scale.
