# Skill: Cloud — Railway (simple full-stack deploy target)

Railway is a PaaS for simple full-stack apps (services + managed Postgres/
Redis) — **not** floci-emulated. Activates at the cloud stage when the recorded
target is `railway`. Philosophy: `skills/platform-engineering.md`.

## Core principle: Docker / Nixpacks parity
Railway builds from a Dockerfile (or Nixpacks). Keep a working local Docker
build; what runs in `docker compose up` is what deploys. No Railway-specifics
in app code.

## Hard rules
- Config via env vars (Railway variables), mirrored in `.env`; reference
  managed-service URLs via Railway's injected vars, never hardcoded.
- Managed Postgres/Redis are provisioned in the Railway project and consumed
  via the injected connection var — defined once, consumed everywhere.
- Services are stateless; persistent data lives in the managed stores or a
  volume, never the container filesystem.
- Secrets only in Railway variables; never in the repo.

## Workflow
1. **Local** — `docker compose up` (app + Postgres/Redis), or `railway run
   <cmd>` to run locally against project vars.
2. **Deploy** — `railway up` / git-triggered deploy to a non-prod environment
   first.
3. **Promote** — Railway environments (dev → prod). Prod + custom domain +
   paid plans = **§5 escalation**.
4. **Verify** — same image local → deploy; parity note in `docs/qa/`.

## Known gaps / gotchas
Usage-based billing (compute + egress) — a §5 cost item; sleep/wake behavior on
lower tiers; single-region by default (latency for distant users).
