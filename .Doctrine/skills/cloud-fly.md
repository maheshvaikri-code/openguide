# Skill: Cloud — Fly.io (containers at the edge)

Fly.io runs containers close to users across regions (Fly Machines) with
managed Postgres and volumes — **not** floci-emulated. Activates at the cloud
stage when the recorded target is `fly`. Philosophy: `skills/platform-engineering.md`.

## Core principle: one Docker image, many regions
The unit is a Docker image declared in `fly.toml`; the same image runs locally
and across Fly regions. Multi-region is config (the regions list), not code.

## Hard rules
- Image + services + regions declared in `fly.toml`; no out-of-band console
  changes.
- Config via `fly secrets` (encrypted) + env; keys mirrored locally; never in
  the repo or baked into image layers.
- Stateless app; state in Fly Postgres or attached volumes — and volumes are
  **region-pinned** (data locality matters for multi-region).
- Health checks defined so Fly can route around unhealthy machines.

## Workflow
1. **Local** — `docker build` + run (`.env` mirrors `fly secrets` keys).
2. **Deploy** — `fly deploy` to a non-prod app first.
3. **Promote** — prod app, scaling, extra regions, custom domains = **§5
   escalation** (paid/external).
4. **Verify** — same image local → Fly; multi-region parity + latency note in
   `docs/qa/`.

## Known gaps / gotchas
Region-pinned volumes complicate multi-region writes (single-writer Postgres +
read replicas); machine cold-start/auto-stop behavior; egress + machine-hours
metered (a §5 cost item).
