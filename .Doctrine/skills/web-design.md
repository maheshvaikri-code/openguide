# Skill: Web Design (professional sites from proven templates + repo content)

**Scope.** Making a repo's public web surface — landing page, docs site, corporate
site — look professionally designed, by **adapting a proven open-source template**
and mapping the repo's own content into it. Distinct from `ui` (in-app component
design) and `web-publishing` (the publish mechanism): this is the *look*. Owned by
the Web Designer role.

## Principles
- **Borrow a proven template; don't invent.** Design quality comes from a
  battle-tested template + disciplined content-mapping, not from an agent
  inventing visuals. Start from the catalog below.
- **License-clean, always.** A borrowed template / font / icon is a dependency —
  check the license (MIT / Apache / CC-BY / …), attribute it, comply
  (`standards/dependency-policy.md`). No license, no ship; attribution-required
  licenses keep their credit line.
- **Content is the repo's, presented well.** Every section maps to real repo
  content — never lorem ipsum. The site says what the repo says, designed.
- **Self-contained beats a CDN.** Bundle CSS, fonts, icons, images; the site must
  render offline and survive a CDN outage (also fewer supply-chain + privacy
  footguns). A missing bundled asset is the classic "logo 404" bug.
- **Consistency over cleverness.** One type scale, one color system, one spacing
  rhythm, light + dark. Accessible by default (contrast, headings, alt, keyboard).

## The corporate-site structure (map repo → sections)
| Section | Sourced from the repo |
|---------|-----------------------|
| Hero | project name + logo + one-line value prop (README h1 + tagline) |
| Features / value | the README's key bullets → a grid of cards |
| Docs / reference | `docs/`, roles, skills, API → navigable pages + sidebar |
| About / how it works | the deeper README sections, architecture |
| CTA | install / quickstart / "get started" |
| Footer | repo link, license, version, contact |

## Template catalog (free / open-source — verify each LICENSE at fetch time)
Borrow from proven, permissively-licensed templates rather than hand-rolling:

- **Docs sites:** *Material for MkDocs* (MIT), *Docusaurus* (MIT), *Nextra* (MIT),
  *Just the Docs* Jekyll theme (MIT), *Docsify* (MIT).
- **Landing / corporate:** *Start Bootstrap* (MIT), *HTML5 UP* (CC-BY 3.0 —
  **attribution required**), *Cruip* free Tailwind templates (license per
  template), *Primer* CSS (MIT), open Tailwind landing kits.
- **Portfolio / project:** *al-folio* (MIT), *Hugo* clean themes (per theme).

Licenses change and vary per template — **verify the actual LICENSE at fetch
time**; CC-BY / attribution-required templates must keep the credit. A closed or
license-unclear template is not usable.

## Do / Don't
**Do:** pick from the catalog + verify its license · map every section to real
content · bundle assets self-contained · one type/color/spacing system · check
contrast + alt text · optimize images.
**Don't:** invent a design when a proven template fits · ship lorem ipsum · strip a
required attribution · depend on a CDN the site cannot survive · ship an
inaccessible "pretty" site.

## Review checklist
- [ ] Template from the catalog; LICENSE checked + attributed
- [ ] Every section = real repo content (no placeholder)
- [ ] Self-contained (assets bundled), renders offline; images optimized
- [ ] One type scale + color system + spacing; responsive; light + dark
- [ ] Accessible (contrast / headings / alt / keyboard)

## Common failure modes
Dev-built CSS that "works" but looks unfinished; lorem ipsum shipped to
production; a stripped CC-BY attribution (a license violation); a CDN-font site
blank offline; a gorgeous but inaccessible site; the logo 404-ing because assets
were not bundled — the exact bug this skill exists to prevent.
