# Skill: MCP Tooling (using external MCP servers, governed)

**Scope.** How a Doctrine-governed agent uses **external** MCP servers as a tool
interface during **any** feature development — GitHub, Docker, cloud providers,
Sentry, databases, browsers, search, whatever the task genuinely needs. Doctrine
already *ships* an MCP server (`doctrineos`, §05-packaging); this skill governs the
reverse: **consuming** other MCP servers safely. It does not replace the work-skills
(`cicd`, `observability`, `cloud-*`) — those describe the *work*; this governs the
*tool*.

## Principles
- **Open-source-first.** Prefer an **open-source** MCP server for a given need — it
  is auditable, self-hostable, free of lock-in, and vettable under
  `standards/dependency-policy.md`. An MCP server is a **dependency**: it clears the
  same bar. A closed/hosted MCP that touches your data is a §5-adjacent decision
  (new third-party data flow) — flag it, don't adopt it silently.
- **Intended, available, else fall back.** Match the MCP to the task's *intent*; use
  it only if a suitable server is actually **available/wired**; if none is (or none is
  open-source-acceptable), fall back to the CLI/SDK the work-skill already assumes, or
  flag the gap. **Never block a task because an MCP isn't wired** — the tool is a
  convenience, not a prerequisite.
- **An MCP action is a governed action.** A tool call that changes the world (merge,
  deploy, delete, spend, send) is a real action under §5 and the non-negotiables —
  routing it through an MCP does not launder it out of the gate.

## The governance overlay (the load-bearing rules)
- **Read-only by default.** Prefer least-privilege / read scopes; use the MCP's read
  tools to *inspect state before any write* — PR status before merge, deploy state
  before deploy, container state before delete.
- **Writes / deploys / spends / deletes / sends = §5 escalation.** Irreversible,
  external, or paid MCP actions stop for the human, exactly like their CLI
  equivalents. The gate is on the *action*, not the tool.
- **Secrets in the server's auth config, never the repo** (non-negotiable #2). MCP
  credentials flow through the agent's MCP configuration; never hardcode a token,
  never echo one into an artifact or log.
- **Attributable + tested.** A behavior change made via MCP still ships with a test;
  the action is logged/attributable; a failed or refused MCP call is an honest status,
  never retried-until-green.
- **Vet before adopt.** A new MCP server passes a lightweight `dependency-policy`
  check — maintenance, **license (open-source preferred)**, scope/permissions, data
  flow. Adopting a data-touching hosted MCP is a §5 external-dependency decision.

## Catalog (illustrative and open — match to intent, prefer open-source, use if available)
| Concern | MCP (examples) | Governance note |
|---------|----------------|-----------------|
| Repo / PR / issues / actions | GitHub MCP | read-only default; PR-merge / release = §5 |
| Containers / images | Docker MCP | build/inspect read-first; prune/delete = §5 |
| Cloud provision / deploy | AWS · Azure · GCP · Vercel MCP (maturity varies) | provision/deploy/spend = §5 (paid/external); local-first still governs (`cloud-*`) |
| Error monitoring | Sentry MCP | read production errors → feeds `observability` / SRE / incident-response |
| anything else | a domain MCP if it fits + is available | databases, browser, search, docs — the same overlay applies |

Do **not** hardcode a per-server skill file (`github-mcp.md`, `docker-mcp.md`, …) —
those rot as APIs change. The catalog is illustrative; it grows by MCP-registry entry
and this one skill, not by new files.

## Do / Don't
**Do:** read before write · least-privilege scope · prefer open-source and vet it ·
fall back to the CLI when no MCP is available · gate every consequential action.
**Don't:** treat an MCP write as ungated · put secrets in the repo · adopt a
closed/hosted data-touching MCP without a §5 flag · build a skill per MCP server ·
block a task because an MCP isn't wired (fall back instead).

## Review checklist
- [ ] MCP chosen matches intent; **open-source preferred**; availability confirmed (else CLI fallback)
- [ ] Read-only / least-privilege scope by default
- [ ] Every write / deploy / spend / delete / send routed through §5
- [ ] No secrets in repo or artifacts; credentials live in the MCP config
- [ ] New MCP server vetted (`dependency-policy`); a data-touching hosted MCP flagged §5

## Common failure modes
Treating an MCP call as "just a tool" and skipping the §5 gate on a deploy/spend;
hardcoding a token to make an MCP "just work"; adopting a flashy closed MCP that
exfiltrates repo/data; a per-server skill that rots; blocking real work because a
preferred MCP isn't installed instead of falling back to the CLI.
