# Skill: Data Architecture

> Load with `roles/data-architect.md`. This is the *modeling* discipline — how
> data is shaped and where it lives. To move data read
> `skills/data-engineering.md`; to implement schema read `skills/database.md`.

## The three model levels — always know which one you're in
1. **Conceptual** — entities and their relationships, in the business's words.
   No keys, no types. The thing a domain expert can read and confirm.
2. **Logical** — normalized or dimensional schema: tables/collections, keys,
   attributes, cardinality, constraints. Engine-agnostic.
3. **Physical** — the realization in a specific engine: partitioning, indexes,
   storage format, sharding, denormalization for access patterns.

Jumping straight to physical is the most common data-design failure: you
optimize a shape before you know what it means.

## Modeling stances
- **Normalization (OLTP).** 3NF as the default for systems of record: each
  fact in one place, integrity by constraint. Denormalize only with a stated
  read pattern that demands it.
- **Dimensional (analytics).** Star/snowflake — facts + conformed dimensions.
  *Conformed* = the same dimension means the same thing across every fact table.
- **Data Vault / wide-table** — when auditability or schema churn dominates;
  choose deliberately and document the tradeoff.

## Storage topology — pick the system of record first
- **OLTP** for transactional truth; **warehouse** for modeled analytics;
  **lakehouse/lake** for raw + semi-structured at volume; **mesh** when domains
  own and serve their own data products.
- Every dataset has exactly **one system of record**; everything else is a
  derived, labeled copy with a refresh contract.
- Name the access patterns each store serves. A store with no stated query
  shape is a landfill.

## Schema evolution — expand/contract, always
- Additive first: add the new column/table, backfill, dual-write, verify.
- Migrate readers, then writers; only then contract (drop the old).
- Never a breaking rename or type change in place. Version the contract; give
  consumers a compatibility window.
- The change ships with its migration *and* its rollback story.

## Canonical definitions
- One definition per business entity/metric. "Active user" is defined once and
  referenced, never re-coined per report. Conflicts are defects (→ Head of Data).
- Capture each entity's definition, grain, and system of record in the
  `data-contract` template at G1.

## Review checklist add-ons
- [ ] Conceptual/logical/physical levels distinguished, not collapsed
- [ ] Every dataset has exactly one named system of record
- [ ] Access patterns stated for each store and index
- [ ] Schema change is expand/contract with a rollback story
- [ ] Every new entity/metric has a single canonical definition + contract
- [ ] Dimensions conformed across fact tables (analytics)
