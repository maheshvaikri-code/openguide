# Skill: Platform Engineering

**Scope.** Building the internal platform as a product: paved roads, shared
substrate, self-service infrastructure, and the deploy-target policy product
teams build on. Distinct from `repo-devops` (one repo's tooling) and from
`resilience`/`incident-response` (SRE): platform engineering owns what is
shared *across* repos.

## Principles
- **Platform as a product.** Developers are customers; adoption is voluntary
  and measured. A paved road nobody takes is a failed product, not a
  disobedient team.
- **Golden path, not golden cage.** The supported path is the easy default;
  every one has a documented escape hatch. Leaving the path signals a gap to
  close, not a rule to enforce.
- **Platform the second use, not the first.** One consumer = a library in that
  repo. Two = a candidate for shared substrate. Speculative platforms rot;
  extract from real duplication.
- **Contracts and versions, always.** Shared substrate has a typed contract
  and a version; cross-repo, it appears in the compatibility manifest
  (`templates/compatibility-manifest.md`). One consumer breaking is a bug; all
  consumers breaking at once is a missing contract.
- **Self-service over tickets.** The platform is a CLI/template/SDK you run,
  not a team you queue behind.

## Paved roads
A paved road is the one supported way to do a common thing (new service,
deploy, auth, telemetry, data access). Define each with
`templates/paved-road.md`: the guarantee it makes, how to use it (one command
/ one template), what it wires by default (doctrine standards, observability,
secrets), and the **escape hatch**.

## Deploy targets — local-first, the PaaS variant
Doctrine is local-first (see the `cloud-<provider>` skills). Major clouds
(AWS/Azure/GCP) emulate via **floci**. **PaaS targets (Vercel, Railway,
Render, Fly.io, …) do not** — floci does not emulate them. The local-first
story for PaaS is instead:
- The app stays **12-factor / portable**: config via env, no provider lock-in
  in app code, one process model that runs the same locally and on the platform.
- **Local dev** via the provider CLI (`vercel dev`, `railway run`, …) or plain
  Docker — same build, same env keys.
- **Promotion ladder:** local → preview/branch deploy → production. Preview
  deploys are the parity check.
- **Elevation = paid/external = §5 escalation.** Real provisioning, custom
  domains, and production deploys are human-gated.
- Pick per workload: Vercel (frontend/serverless), Railway (simplest
  full-stack), Render (managed full-stack + workers/cron), Fly.io (containers
  at the edge). See `skills/cloud-<provider>.md`.

## Do
- Extract substrate from real duplication; give it a version + contract + owner.
- Make the doctrine's standards the *default* in scaffolds/templates, so
  compliance is free.
- Measure DevEx: time-to-first-green, time-to-deploy, onboarding time
  (`skills/metrics.md`).
- Provide an escape hatch and watch who uses it — that is your backlog.

## Don't
- Don't platform a one-consumer capability, or mandate a path with no exit.
- Don't ship a platform as a ticket queue; ship it as self-service.
- Don't let shared substrate go un-versioned; a silent breaking change hits
  every consumer at once.
- Don't confuse platform work with per-repo DevOps or with SRE reliability —
  different owners, different gates.

## Review checklist
- [ ] Paved road defined via template, with escape hatch
- [ ] Substrate versioned + contract-pinned (+ compatibility manifest if cross-repo)
- [ ] ≥2 real consumers before platforming
- [ ] PaaS local-first honored; elevation escalates (§5)
- [ ] DevEx metric present

## Common failure modes
The golden cage (mandate, no exit); the speculative platform (built for
imagined reuse); the copy-paste "platform" (shared config, no contract); the
ticket-queue platform (not self-service); version-less substrate that breaks
everyone on one change.
