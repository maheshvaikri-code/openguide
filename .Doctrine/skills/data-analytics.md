# Skill: Data Analytics (data → decisions)

**Scope.** Deriving honest, actionable insight from data — analysis, SQL/BI,
dashboards, metric definition, and experimentation. Distinct from
`data-engineering` (moves + stores data) and `metrics` (measures the *process*, not
the business). Owned by the Data Analyst.

## Principles
- **Decision-first.** Every analysis names the decision it serves before the first
  query. No decision → don't build it.
- **One metric, one definition, one query.** Define it, own it, version it.
  Ambiguity ("active user" = ?) is how confident-wrong calls happen.
- **Honest statistics or silence.** Report sample size, uncertainty
  (interval/significance), and confounders. Never a point estimate with no baseline;
  never correlation dressed as causation.
- **Reproducible.** The query/notebook is committed and re-runs to the same number.
  An unrepeatable analysis is an opinion.
- **Privacy-bound.** PII in analysis follows `privacy-compliance` — aggregate,
  minimize, and never export raw personal data into a dashboard.

## The analysis workflow
1. **Question** — the decision + who acts on it + what answer would change it.
2. **Define** — the metric(s), grain, filters, time window; write the definition down.
3. **Query** — SQL/notebook against the warehouse (`data-engineering` supplies it);
   validate row counts + spot-check before trusting it.
4. **Analyze** — segment / cohort / funnel / trend; test significance where claimed.
5. **Read out** — the number, the interval, the "so what," the recommendation, and
   what would change it. Evidence-linked, reproducible.

## Experimentation (A/B)
Hypothesis → primary metric + guardrail metrics → power / sample size
(**pre-declared**) → randomization + exposure check → **pre-registered** analysis →
readout with effect size + interval. No peeking-and-stopping, no post-hoc metric
swaps — **p-hacking is a §1 honesty violation, not a technique.**

## Dashboards / BI
A dashboard answers a standing question for a named audience. Every tile traces to a
**defined** metric; no vanity tiles; a slow query is a bug. Prefer a few
decision-driving views over many that nobody acts on.

## Do / Don't
**Do:** state the decision · define the metric once · report uncertainty · commit the
query · aggregate PII. **Don't:** p-hack · sell correlation as causation · ship a
metric with three meanings · build a dashboard nobody decides from · put raw PII in a
report.

## Review checklist
- [ ] Decision named; metric defined (one definition / query / owner)
- [ ] Uncertainty + confounders reported; no correlation-as-causation
- [ ] Experiment pre-registered (hypothesis / guardrails / power) if claimed
- [ ] Query / notebook committed + reproducible
- [ ] PII aggregated / minimized (`privacy-compliance`)

## Common failure modes
The p-hacked win (stopped when it looked good); the metric that means three things;
correlation sold as cause; the dashboard nobody decides from; the unrepeatable
"insight"; raw PII exported into a chart.
